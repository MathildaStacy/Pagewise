# 产品审查与改进方案 · v0.0.11

审查日期：2026-11-01。基线：`996be9d`（main，应用代码为 v0.0.11）。方式：只读检查文档、源码、分支、tag 与 CI 记录，没有修改业务代码，也没有运行 App 或调用真实 AI / MinerU。

本文从产品角度补充两份已有审查：[逻辑与 UI 审查](evidence/main-audit-b213f6d/REPORT.md)（B01–B09、U01–U04）和 [视觉设计审查](evidence/main-audit-b213f6d/VISUAL_DESIGN.md)（V01–V05）。那两份报告列过的缺陷这里不重复计数，只在影响产品决策时引用。

## 结论

**核心伴读循环已经做出来，工程质量也高（2,004 项测试、CI 全绿、证据完整）；现在的主要问题不在单个缺陷，而在产品层面的四件事：**

1. **能力和皮肤绑在一起。** 新手引导、「今天」、问书架（跨书检索 + AI 回答）、学习记录只在 Win11 皮肤里有入口。默认皮肤是纸感，新装用户看不到这些功能。
2. **功能增长快于 V1 验收。** 41 小时内发了 11 个预览版，新增三套皮肤、整节翻译、AI 精修、章节多对话、代码阅读；`07-plan.md` 的 52 条验收中仍有 32 条未勾选，PRODUCT_DESIGN 的四个目标 G1–G4 目前都不能判定达成。
3. **本地优先，却没有兜底。** 学习记录只存在手机上，没有自动备份，也没有备份提醒；release 包用仓库里的 debug 签名，将来换签名需要卸载重装，会清空数据。
4. **「真相来源」不清楚。** README、PRODUCT_DESIGN、dev/README 和代码互相矛盾；修好长对话历史（B08）的分支停在 10-30 没有合入。

**建议用大约两周做一次「V1 收口」：** 冻结新功能，先修数据安全问题、补齐入口、加备份提醒，再真实使用两周并补完验收，最后更新文档。具体路线见文末。

## P1 问题

### PM-01 · 四项能力只在 Win11 皮肤可达

**现状**

| 能力 | 唯一入口 | 皮肤判断位置 |
| --- | --- | --- |
| 首次启动的新手引导（配置 AI、MinerU、讲解偏好三步） | 空书库首次启动时自动打开 | [HomeScreens.tsx:29](../../src/features/home/HomeScreens.tsx#L29) `skin.id !== 'win11'` 时直接返回 |
| 「今天」页（续学、待复习、连续天数、卡点） | 底部第五个 Tab | [RootNavigator.tsx:174](../../src/ui/navigation/RootNavigator.tsx#L174)、[:217](../../src/ui/navigation/RootNavigator.tsx#L217) |
| 问书架：跨书全文检索 + AI 回答 | 「今天」页顶部输入框 | [TodayView.tsx:63](../../src/ui/screens/TodayView.tsx#L63) |
| 学习记录：连续天数、每日目标、学习时长 | 「今天」统计卡；「我的 → 学习记录」 | [useSettingsVM.ts:236](../../src/features/settings/useSettingsVM.ts#L236) 只给 Win11 插入这一行 |

默认皮肤是纸感（[appearance.ts:19](../../src/app/appearance.ts#L19)）。其他四套皮肤的书架搜索只按书名和作者过滤（[useLibraryVM.ts:208](../../src/features/library/useLibraryVM.ts#L208)）。学习时长在所有皮肤都会记录（[StudyScreens.tsx:17](../../src/features/study/StudyScreens.tsx#L17)），只是看不到。

**影响**

- 新装后默认是纸感，没有任何引导；用户导入书、进入听讲，第一次请求 AI 才看到报错（见 PM-05）。
- 换皮肤会改变「能做什么」，这和 [02-skins.md](02-skins.md) §2 的原则「用户换皮肤后不需要重新学怎么用」相反。
- 「这个概念在我哪本书里讲过」正是技术书精读的高频问题，但五套皮肤里有四套用不了问书架。

**建议**

1. 新手引导与皮肤无关：所有皮肤在「空书库 + 未完成引导」时都打开 Welcome。[WelcomeView](../../src/ui/screens/WelcomeView.tsx) 只用 kit 组件和 `MeView` 的设置行，结束时 `nav.replace({ tab: 'Today' })` 在非 Win11 皮肤下会被 [RootNavigator.tsx:178](../../src/ui/navigation/RootNavigator.tsx#L178) 重定向回书架，改动面很小。「我的 → 关于」上方的「新手引导」入口也对所有皮肤开放。
2. 问书架：在每套皮肤的书架搜索浮层里增加「在书里搜 / 问 AI」一栏，复用 `searchShelf` / `answerShelf`。
3. 学习记录：「我的」页对所有皮肤显示「学习记录」一行。
4. 「今天」页可以继续作为 Win11 的独有构图；要求是页面上的每项能力在其他皮肤都另有入口。
5. 增加一条契约测试：`RootStackParams` 中的每个面向用户的路由，在五套皮肤下都至少有一个入口。

**验收**：纸感新装，2 次点击以内能进入新手引导、问书架和学习记录；五套皮肤的可用功能清单一致。

### PM-02 · V1 验收停滞，新功能持续叠加

**现状**

- [07-plan.md](07-plan.md) 共 52 条验收：T0–T3、T5 的 20 条已勾选；T4、T6–T12 的 32 条未勾选。[验收状态矩阵](evidence/t12/acceptance-status.md) 记录了其中一部分的模拟器证据，但以下几项仍然没有真实结果：Anki 程序实际导入、真实隔 3 天续学、30 条原生引用点击、PDF 重新解析后的迁移、Anthropic 缓存、实体机冷启动与滚动帧率。
- 同期加入的功能大多不在 V1 计划里：Meta / 新谷歌 / Win11 三套皮肤（07-plan「不在 V1 范围」明确写了「更多皮肤」）、整节翻译、AI 精修、章节多对话、模型推理 / 搜索选项、IDE 风格代码阅读、「今天」与连续天数。
- v0.0.1（10-29 13:20）到 v0.0.11（10-31 06:38），41 小时内发了 11 个预览版。
- 主线审查的三个 P1（B01 取消高亮删除笔记、B02 已学退回在学、B03 笔记写入失败后持续不可读）都直接违反产品原则「学过的要留下」。

**影响**

PRODUCT_DESIGN 的四个目标目前都不能判定达成：

| 目标 | 已有证据 | 缺口 |
| --- | --- | --- |
| G1 一节一节读懂一本书 | 真实书 3 个小节的自动化 harness 通过（[native-real-study.json](evidence/t7/native-real-study.json)） | 没有负责人真人学完一章的记录；讲解质量没有人工评价 |
| G2 回答可追溯 | 58 条引用校验 0 失败；30 块源坐标人工核对通过 | 原生界面里点引用、跳到正确位置的路径没有走完 |
| G3 隔几天能接上 | Demo 的「距上次 3 天」 | 没有真实隔 3 天后 1 分钟内接上的记录 |
| G4 学过的能留下 | Markdown / CSV 文件内容正确 | Anki 实际导入未做；B01、B03 会丢失或读不到笔记 |

每多一个功能，就多一份 5 套皮肤 × 浅深色的回归量，未完成的验收会越来越难补。

**建议**

1. 宣布两周「V1 收口期」，期间只合入 P1 / P2 修复、验收补测和本文 PM-01、PM-03、PM-05。
2. 收口顺序：B01–B03 → B04（阅读位置）→ PM-01 → 真实隔 3 天续学与 Anki 导入 → 原生引用点击抽样。
3. 把 07-plan 的复选框和状态矩阵对齐：已有证据的勾上并链接证据；做不了的写明「移出 V1」和原因（例如 Anthropic 专项缺可用服务）。
4. 每份 release note 增加一行「V1 验收：已通过 x / 剩余 y」。

**验收**：07-plan 每一条都是「通过（附证据）」或「移出 V1（附原因）」；G1–G4 各有一条真实使用记录。

### PM-03 · 学习记录没有自动备份或提醒

**现状**：产品没有后端，书、学习记录、闪卡、笔记都只在本机 SQLite 中。[AndroidManifest.xml:10](../../android/app/src/main/AndroidManifest.xml#L10) 设置 `allowBackup="false"`；备份只能在「我的 → 存储」手动导出，代码里只记录最近一次导出时间（[storage.ts:238](../../src/app/usecases/storage.ts#L238)），没有定时备份或提醒。

**影响**：手机丢失、误清应用数据、或将来因换签名必须卸载重装（PM-09），都会清空全部学习记录。对一个目标是「隔几天能接上」「学过的要留下」的产品，这是最大的单点风险。B01 / B03 已经说明笔记存在丢失路径，没有备份就无法挽回。

**建议**

1. **先做（成本很低）：备份提醒。** 距最近一次成功备份 ≥ 7 天，并且之后有新的学习记录时，在书架顶部显示一条可关闭的提示「上次备份是 9 天前，现在备份？」，点一下直接导出。
2. **再做：自动备份到用户选的文件夹。** 通过 SAF 让用户选一个持久授权的目录（例如网盘同步目录），每天首次打开时写一份，保留最近 N 份。现有备份不含 Key 和 Token（[备份恢复记录](evidence/t11/native-uninstall-restore.json)），放到外部目录不会泄露凭据。
3. 不建议直接打开 Android Auto Backup：要另外确认规则只包含数据库，排除 Keystore 相关文件，验证成本更高。

**验收**：模拟最近 8 天没有备份，书架出现提示；点击后备份成功，提示消失。

### PM-05 · 首次使用缺引导，报错文案指错方向

**现状**（以默认纸感为例）：

- 没有分配 AI 模型时，[container.ts:80](../../src/app/container.ts#L80) 抛出的原文是「请先在「我的 → AI 服务」分配讲解模型和整理模型」，写得很清楚；但 [StudySession.ts:253](../../src/app/study/StudySession.ts#L253) 经过 `toAppError` 后，按错误码 `bad_request` 换成固定文案「AI 服务不接受这个请求，请检查模型和服务设置」（[errors.ts:28](../../src/app/errors.ts#L28)），原来的提示丢了。
- 配了服务但没填 Key 时，错误码是 `auth`，用户看到的是「AI 服务的 Key 无效或已过期」。对从没填过 Key 的人，这句话方向不对。
- 学习页的错误下面只有一行文字「可在「我的 → AI 服务」检查模型与密钥」（[StudyView.tsx:515](../../src/ui/screens/StudyView.tsx#L515)），没有可点的入口。
- 导入 PDF 时不检查 Token；上传确认框写着「使用你在「我的 → 解析服务」里配置的 Token」（[ImportSettingsView.tsx:234](../../src/ui/screens/ImportSettingsView.tsx#L234)），即使还没配置。失败要到解析进度页才出现，好在那里有「去更新 Token」。

**建议**

1. 新增「未配置」错误（`ai.not_configured`、`mineru.missing_token`），和「Key 无效」分开，文案说「还没配置」而不是「配错了」。
2. 学习页、翻译面板、精修面板遇到可通过设置解决的错误时，显示「去设置」按钮，直达 `MeAI` / `MeMineru`。
3. 导入设置页在没有 Token 时，把「开始解析」换成「先配置 MinerU Token」；EPUB 不受影响。
4. 和 PM-01 一起做：新手引导覆盖所有皮肤后，大部分新用户不会走到这些报错。

**验收**：纸感新装、不做任何配置，导入 PDF 和进入听讲时看到的都是「还没配置」以及能点的「去设置」。

### PM-07 · 没有衡量「读懂了没有」的数据

**现状**：本机只记录了学习时长（按天）和复习调度。以下数据都没有：每本书已学小节随时间的变化、续学从打开到进入上次位置的耗时、引用点击次数与跳转结果、卡点的产生与划掉、AI 请求失败率与原因。「学习记录」页只在 Win11 可见（PM-01）。

**影响**：M4 的验收是「连续 2 周每天使用」，G3 是「1 分钟内接上」，目前都没有数据可以判断。产品方向只能凭印象调整，新功能是否值得做也没有依据。

**建议**

1. 在本机加一张轻量事件表，只记事件类型、时间、书 / 小节 ID 和少量数值，不记正文、问题或回答，不联网：
   - `open_book`、`resume`（距上次天数、到达上次位置的秒数）
   - `section_done`、`citation_tap`（是否跳到目标块）
   - `review_done`（张数、忘记比例）、`stuck_added` / `stuck_cleared`
   - `ai_error`（错误码）
2. 「学习记录」页按书汇总：已学小节趋势、平均续学耗时、卡点净变化、AI 失败率。
3. 收口期每天写一条简短试用日志（读了什么、哪里卡住、哪里不顺），放在 `docs/dev/dogfood/`。两周的真人记录比再跑一轮 harness 更能说明 G1–G3。

### PM-08 · 五套皮肤使验证成本成倍增长

**现状**：5 套皮肤 × 浅深色 = 10 种组合。`src/ui/screens/` 中有 92 处 `brand.kind` / `skin.id` 判断；[brand/components.tsx](../../src/ui/skins/brand/components.tsx) 2,228 行、[glass/components.tsx](../../src/ui/skins/glass/components.tsx) 1,521 行。同一个模式开关，纸感叫「伴读 | 原文」（[controls.tsx:322](../../src/ui/kit/base/controls.tsx#L322)），其他四套叫「读书 | 听讲」，顺序也相反。视觉审查 V03、V05 已发现共享页面没有适配某些皮肤的底材。

**影响**：每次 UI 改动都要在 10 种组合下回归，PM-02 的验收缺口和这一点直接相关。用户换皮肤后，最核心的模式开关名字和位置都变了。

**建议**（五套皮肤是已定方向，这里不建议删减）

1. 负责人指定一套日常主力皮肤。每次发版对它做完整原生走查；其余四套依靠自动渲染快照和对比度测试，只在改动共享页面或该皮肤组件时才做原生走查。
2. 页面里的皮肤判断逐步下沉为 token 或 `layout` 字段；加一条 lint 规则，禁止 `src/ui/screens` 新增 `brand.kind ===` 判断。
3. 模式命名：请负责人确认纸感的「伴读 | 原文」是否仍是硬约束（10-29 要求「严格遵循原型」）。如果不是，统一为「读书 | 听讲」并统一顺序；内部状态已经是 `read` / `listen`，改动只在文案层。

### PM-09 · 版本号和签名不规范

**现状**

- `v0.0.12` 是附注 tag，说明写的是「Application code remains at v0.0.11」，`package.json` 和 versionCode 也还是 0.0.11 / 11。可安装版本和文档快照共用同一个 tag 序列。
- [releases/](releases/) 只有 8 份说明，缺 v0.0.3、v0.0.6、v0.0.10、v0.0.12。
- release 构建使用仓库里提交的 `android/app/debug.keystore`（[build.gradle:103](../../android/app/build.gradle#L103)，旁边还留着 RN 模板的「In production, you need to generate your own keystore」注释）。

**影响**：看 tag 无法判断哪个版本能装。debug keystore 是公开的，任何人都能签出可以覆盖安装的包。将来改用正式签名时，已安装的应用必须卸载才能装新包，卸载会清空学习记录，和 PM-03 叠加成数据丢失风险。

**建议**

1. tag 只给可安装的构建；文档快照用 `audit-YYYYMMDD` 之类的 tag，或者不打 tag。
2. 补齐缺失的 release note；没有安装包的版本写明「仅文档」。
3. 趁现在只有一个用户，生成正式 release keystore（存 CI secret，不进仓库）。切换步骤写进发布文档：备份 → 卸载 → 安装新签名版本 → 恢复。应在 PM-03 的备份提醒上线之后进行。

### PM-10 · 冷启动远超目标，实体机从未测过

**现状**：目标是中端实体机 release 冷启动 < 1.5 秒；模拟器三次分别为 9,320 / 3,828 / 4,323 ms（[报告](evidence/t12/release-cold-start-emulator.json)），而且这只是首帧时间，不是可交互时间。实体机没有测过。

**影响**：产品场景是通勤、午休、睡前的 5–15 分钟。打开要 4 秒以上，会直接降低「顺手打开读两页」的意愿，属于产品问题，不只是性能指标。REPORT 的性能项也提到书架会等待旧书封面生成。

**建议**：收口期在一台常用的实体机上测 release 冷启动和「打开到续学卡可点」两个时间，各测 5 次。如果超过 2 秒，优先处理书架首屏不等待封面和其他非必要查询（REPORT 性能项 1），再看启动阶段的初始化顺序。

## P3 问题

### PM-11 · 书的地图有大量黄色待核对，只能逐项处理

**现状**：按 [product-experience.md](product-experience.md)，真实样本在过滤字号误报后仍有 145 处待核对。地图页显示「N 处需要你确认 · 点开黄色标记逐项核对」（[presenters.ts:343](../../src/features/library/presenters.ts#L343)），每处要单独打开对话框处理。

**建议**：按章显示待核对数量，提供「本章按书签目录全部确认」；还没读到的章节弱化黄色提示，只在进入该章前提醒。不影响已确认项和学习位置。

### PM-12 · 「每天提醒」在真实书库中是灰的

**现状**：[LearningStatsView.tsx:233](../../src/ui/screens/LearningStatsView.tsx#L233) 的开关在真实书库中禁用，副标题写「本机通知尚未接入，可在演示书库预览」；演示书库里却显示「21:00 · 本机通知，不联网」。文案如实，但界面上放了一个不能用的功能。

**建议**：间隔重复的效果依赖按时复习，提醒有实际价值。接入本机定时通知，内容用当天到期的闪卡数（「今天有 12 张卡要复习」），没有到期卡就不提醒。如果短期不做，在真实书库隐藏这一行。

### PM-13 · 用量只显示 token，没有金额

**现状**：「我的 → AI 服务 → 用量」按书和本月显示 token 与缓存命中（[MeAIView.tsx:166](../../src/ui/screens/MeAIView.tsx#L166)）。PRODUCT_DESIGN §6.7 的目的是「方便估算费用」，但用户需要自己换算。

**建议**：每个 AI 服务可选填单价（输入 / 输出 / 缓存读取，每百万 token）；填了就在用量页显示估算金额。整节翻译、原页复核这类大请求开始前显示「约 N 千 token」。不填单价时保持现状。

### PM-14 · 证据目录 131 MB 进了仓库

**现状**：`docs/dev/evidence/` 有 761 个文件，约 131 MB，主要是 PNG 截图、XML 层级和构建日志；`.git` 已有 139 MB。learning-harness 分支还在加入大量评测 JSON。

**建议**：仓库里每轮只保留 README、结论 JSON 和少量关键截图；原始截图和日志放到 GitHub Release 附件或仓库外的存档目录，README 记录链接和 SHA-256。新证据按此执行，旧证据可以不迁移。
